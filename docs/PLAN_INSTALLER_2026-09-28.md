### 1.4 The compile the executor uses, and what every build is

Every build since Stage 2 of Phase 2 is compiled from source on this machine, inside a worktree, by the program folder compiler, and the resulting ex5 is copied into the data folder by the owner. The command, as the enforcement plan writes it for ENF-S1: "`metaeditor64.exe /compile:<wt>\MQL5\Experts\AccountGuardian\AccountGuardian.mq5 /include:<wt>\MQL5 /log:<jobtmp>\metaeditor.log`, and both vector scripts" (`ENFPLAN:464`); as the build entries record it: "the compiler invoked is `C:\Program Files\MetaTrader 5\metaeditor64.exe`, the program folder, with `/include` rooted at the worktree `MQL5` tree and `/log` under the job tmp directory" (`LEDGER.md:200`, `:221`).

Four measured facts govern any compile on any machine.

ONE, the include root. Without the switch, "the include root follows MetaEditor's configured data folder and not the compiled file's tree", measured as `Result: 101 errors, 12 warnings` when a worktree script compiled against the deployed Phase 1 `Persist.mqh`; "Adding `/inc:` pointing at the worktree's own `MQL5` directory fixes it completely" (`LEDGER.md:1536`). An earlier session had also seen error 106 "file not found" when compiling a file outside any MQL5 root (`LEDGER.md:1752`, `:1792`). The PK build's static row confirms the current tree includes nothing outside itself: "every `including` line names a path under the worktree ... zero standard library lines" (`LEDGER.md:150`).

TWO, standing rule 6: "the metaeditor64.exe process exit code is NOT a compile status signal and is inverted in practice on this installation. Measured with a control: the real build logged "Result: 0 errors, 0 warnings" and exited 1, while a deliberately broken copy of the same source logged "Result: 3 errors, 0 warnings" and exited 0, producing no ex5 ... The authoritative signals are the log's Result line and the presence and timestamp of the ex5, and both must be read." (`LEDGER.md:2004`)

THREE, standing rule 7: "the ex5 SIZE AND HASH ARE NOT BUILD IDENTITY. Five consecutive compiles of byte-identical source ... produced five different binaries ... Build identity rests on three things instead: the md5 of every source file against the committed tree, the ex5 modification timestamp, and the runtime behaviour of the loaded image in the journal" (`LEDGER.md:2004`). The ex5 never enters git: "`.gitignore:8` carrying `*.ex5`, so no binary enters history" (`LEDGER.md:917`).

FOUR, line endings. `.gitattributes` is `* text=auto` and `core.autocrlf` is `true`, so "`git show` emits the LF normalized blob while the file the owner actually copies carries CRLF" (`LEDGER.md:1310`, `:1750`). Measured this session for the EA at `2be5606`: the working copy is 80501 bytes, md5 `31C76C5F40AA4A63E260B97738224CB8`, the value the PK build entry records (`LEDGER.md:151`); the committed blob is 79060 bytes, md5 `F351382877BDB4ECDA4056F401E92442`, zero carriage returns; both begin with the UTF-8 BOM `EF BB BF`. So the md5 of the same committed source differs by 1441 bytes depending on how it reached a disk.

Two further measured facts about what happens when a new ex5 lands under a RUNNING terminal. When MetaEditor wrote a new `AccountGuardian.ex5` inside the terminal tree, the terminal reloaded the attached EA by itself: "an EA reload the terminal performed by itself the moment MetaEditor wrote the new `.ex5`, seven seconds before any human acted" (`LEDGER.md:1320`), seen again at `:1340`. When the owner instead overwrote the ex5 with a plain copy, the running EA was not reloaded and kept running until the ordered restart: "it places the copy THREE MINUTES AND FORTY SIX SECONDS BEFORE THE CLEAN DEINIT. Order is copy, deinit, shutdown, start, init." (`LEDGER.md:369-375`), and "there was no hot reload of a replaced ex5" (`LEDGER.md:248`).

### 2.1 How MetaTrader 5 installs on Windows

- Default program folder: "if the Client Terminal is installed in the "C:\Program Files\MetaTrader 5\" folder" [DOC https://www.mql5.com/en/articles/311]. The installation help page does not print the literal path; it says "When the installer is launched with the /auto key... the terminal will be installed at the standard path" and "You can specify another directory for the platform installation in automatic mode using the additional key /path" [DOC https://www.metatrader5.com/en/terminal/help/start_advanced/installation]. - Broker branded installers use their own folder names: UNSOURCED on any MetaQuotes page; a third party uninstaller site shows an example, "C:\Program Files\Axi MetaTrader 5 Terminal\uninstall.exe".
- Several installs on one machine: "Two copies of the platform cannot run from the same directory. If you need to run multiple copies at the same time, install the appropriate number of programs in different directories." [DOC https://www.metatrader5.com/en/terminal/help/start_advanced/start]

### 2.2 The data folder

- Location and id: "C:\Users\username\AppData\Roaming\MetaQuotes\Terminal\instance_id\" and "'instance_id' is a unique identifier generated based on the path to the directory where the platform is installed." [DOC .../start_advanced/start]. The algorithm is UNSOURCED. So the id is stable per install path and cannot be predicted by an installer without the algorithm; it can only be found.
- `origin.txt`: "Each data folder contains a special text file origin.txt. This file contains the path to the platform installation folder, which corresponds to this data directory." [DOC .../start_advanced/start, and https://www.metatrader5.com/en/metaeditor/help/beginning/open]. Measured on the owner's machine: one `origin.txt` at the data folder root (`LEDGER.md:170`); its content is not on record.
- Per Windows account: "In the main mode, the catalog where editable files are stored is different for each Windows account." [DOC .../start_advanced/start]. So a second Windows account on one machine has its own data folders under its own `%APPDATA%`, which IN-27 relies on.
- Common folder: `TERMINAL_COMMONDATA_PATH` is the "Common path for all of the terminals installed on a computer" [DOC https://www.mql5.com/en/docs/constants/environment_state/terminalstatus]; the `Community` folder seen on the owner's machine is UNSOURCED. The guardian uses neither: no `FILE_COMMON` flag exists in the tree (source read, `Persist.mqh` opens files under `AccountGuardian\` only).

### 2.3 Portable mode

- "start the platform from the command line with the additional /portable key", which lets "you ... force the platform to store its data in the installation folder" [DOC .../start_advanced/start].
- Conditions: "If the platform is installed in the Program Files folder, the user must have administrator rights on the computer. In addition, UAC (User Account Control) must be disabled... If the platform is installed in any other folder, the user must have permission to write data to that folder." and "if the platform is installed in the Program Files directory and user rights to write to that directory are limited, it is run in the main mode." [DOC same page].
- An automatic fallback to portable mode is not documented. Files are not migrated between modes: "no files from the user directory are transferred to the installation one after launching in the Portable mode" [DOC .../metaeditor/help/beginning/open].
- Consequence for detection: a portable terminal has no folder under `%APPDATA%\MetaQuotes\Terminal`, so a detection that only scans there reports it absent (IN-9, IN-11).

### 2.4 Detecting an installed terminal, and picking one when there are several

- Registry: no MetaQuotes page documents the keys the installer writes. UNSOURCED; a third party page lists `HKEY_CURRENT_USER\Software\MetaQuotes Software\MetaTrader 5` and `HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\Uninstall\MetaTrader 5`. A broker branded install would carry its own names, also UNSOURCED.

So the documented way to list terminals a Windows account has used is to list the subfolders of `%APPDATA%\MetaQuotes\Terminal` that carry an `origin.txt`, and read each one's program path. A terminal installed and never started by this account has no data folder yet; a portable terminal has none there at all.

### 2.5 What metaeditor64.exe needs to compile from a path outside the data folder

## TASK 3, design space

Each option says what it does, what it cannot do, and what it costs. None is preferred.

### 3.1 The artifact: compiled, source, or both

**(a) Ship the compiled ex5 and copy it.** The owner compiles `AccountGuardian.ex5` (and, if IN-18 ships it, `AgPhase2StateVectors.ex5`) at a tagged commit, the customer's installer copies it into `MQL5\Experts\AccountGuardian\`. Does: no compiler on the customer's side, no include resolution, no Result line to parse, a fixed md5 the installer can check the landed file against, the same shape as the five deploy scripts. Cannot: let the customer verify the binary against the source, since standing rule 7 says no ex5 is build identity and a customer compile of the same source yields a different md5 (P108); cannot adapt to a terminal build whose runtime rejects an older or newer ex5, a compatibility the documentation read this session does not state (UNSOURCED). Cost: the ex5 must live somewhere the customer can fetch (IN-4): `.gitignore:8` keeps every `*.ex5` out of git, so committing one needs an ignore exception, and a Release asset needs the owner to publish a Release; each release is one more owner compile and publish.

**(b) Ship source only and compile on the customer's machine with their own MetaEditor**, verifying by the md5 of each source file and a clean Result line. This is what this project does today on its own machine (1.4). Does: the customer runs code built from the source they can read; the build label `init|build=<label>` in their own journal names what runs; nothing binary is published. Cannot: guarantee the customer's compiler build behaves like build 6230's (unmeasured); cannot rely on the exit code (standing rule 6, measured on this installation only); cannot give one md5 per source file independent of the channel, since a clone with `core.autocrlf=true` writes CRLF and an archive writes LF (1.4, 2.11, P109). Cost: the installer must locate `metaeditor64.exe` (next to `terminal64.exe` per `origin.txt`), run it with `/compile`, `/include` rooted at the repository's `MQL5` folder and `/log`, parse a log whose encoding is UNSOURCED, and decide where the ex5 lands (IN-5).

**(c) Both, the source compile first and the shipped ex5 as the fallback when the compile fails**, or the reverse order, the shipped ex5 first and a source compile offered. Does: covers a customer whose MetaEditor is missing or whose compile fails. Cannot: make the two artifacts identical (rule 7), so a customer's journal may show the same `init|build=<label>` from two different binaries, one of them unverifiable against source. Cost: both costs above plus the rule that picks one, and one manifest carrying source md5s and the ex5 md5 for the same commit.

### 3.2 Distribution

**git clone.** Versioned, updatable with `git pull`, the working copy is CRLF under the default Windows git setting. Presumes git is installed (2.11). Carries the whole history, including every public governance file (3.3).

**A GitHub Release zip per tagged version.** Versioned by tag, can carry the source archive and any asset such as an ex5 or a checksums file (2.11). Each release is an owner act. The same Mark of the Web consequence as the ZIP.

**A one line download**, for example a PowerShell command that fetches and runs a script. Does: one thing to paste. Cannot: let the customer read what runs before it runs; downloads through `Invoke-WebRequest` may not carry the Mark of the Web (2.10), which removes the one Windows prompt a customer would otherwise see. Cost: the "touches nothing" promise begins only after the download, and the command itself is network code, a class every other option keeps out of the installer (3.6).

In every channel, what the customer's disk holds is bytes whose md5 depends on the channel. A manifest must say which bytes it hashes (IN-6).
