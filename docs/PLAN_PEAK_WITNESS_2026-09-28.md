### 1.2 `LEDGER.md:1440`, the STAGE 4 boot derivation entry, quoted whole, DERIVED as the authority

> STAGE 4, THE BOOT DERIVATION. `AgBootDerivation` runs at the SYNCING exit and ORs three witnesses with STRICTEST WINNING on duration. FILE witness fires on `locked_until > now` rather than on the reason field, so an expired lock's stale record reads as not-locked and needs no clear-on-unlock rewrite. GV witness carries a bare timestamp and therefore defaults to DAILY_BREACH, a GV having no CORRUPT_STATE concept to express. DERIVED witness replays broker history and is the AUTHORITY, precisely because a local machine attacker cannot forge or delete server side history while the file and the GV are both locally writable and are therefore accelerators rather than authority. CORRUPT_STATE takes the reason on a tie, because a DAILY_BREACH label would hide the one thing that finding says, that the record cannot be trusted. THE OR ONLY ADDS A LOCK: no witness unlocks, unlock remains exclusively the `TimeCurrent >= locked_until` comparison, and an unevaluable replay returns a third code that holds the EA in SYNCING rather than licensing an unlock, which is the F6 obligation made structural rather than advisory.

This is the authority ordering the whole gap sits inside: the peak is not part of what DERIVED replays (TASK 2.2), so on a peak path lock DERIVED is silent and the authority is silent, leaving only the two accelerators.

**(c1), deals only, inside the same walk.** Extend `AgRealizedRunFold`'s existing per-deal loop (`Pnl.mqh:151-178`) with one more read per deal, `HistoryDealGetInteger(ticket, DEAL_MAGIC)`, and track the LATEST deal time whose magic equals `AG_SWEEP_MAGIC`; if any such deal exists today, a lock is DERIVABLE with `until = AgApplyLatchFloor(AgNextDayAnchor(that deal's DEAL_TIME))`, reason a value TASK 4 names (PK-9). Worked: LOCK ONE, sweep deals #456070002/#456070125/#456070288 at 15:28:17-19 server (`journal-20260923-enf-lock-one.txt:181` region, terminal `:96-113` region per `LEDGER.md:152`); a relaunch at any point after `:181` finds these deals and derives a lock. LOCK TWO, sweep deals #471522444/#471522459 at 16:35:37-38 server (`:152-155`, terminal `:13-20`); same result. **Cost:** one more integer read per deal inside a fold that already runs once per boot, not per tick (2.2); no second walk (satisfies the shape 1 precedent per 1.7). **What it misses:** a lock whose sweep sent NOTHING, because every ticket was held the whole session (AutoTrading off throughout, or every symbol's session closed the whole window, `ENFPLAN:398` names this class), which leaves no `AG_SWEEP_MAGIC` deal on record at all; and ruling THREE's longer `locked_until` (a frozen-quote extension, `EA:442-443`) is not recoverable from a deal timestamp, since the witness only knows when the CLOSE happened, not whether the quote was frozen at the ORIGINAL breach instant.

**Closes:** opening TWO in full, for any lock whose sweep sent at least one close (or, under c2, any send at all); opening ONE narrows to the tick between the lock's own declaration and its first successful send, which under trigger (b) (`ENFPLAN:378`, already ratified ENF-1(b)) is at most one tick after LOCKED regardless. **Leaves open:** the zero-send lock named above (c1), fully closed only by AutoTrading having been off or every symbol closed for the ENTIRE window between breach and drill, itself a further tamper posture question (overlaps (d)); ruling THREE's longer `until` is never recoverable exactly, only approximated from the deal or order timestamp. **FINAL touched:** shape 1's frozen signature, under (c2) only, named and not ruled (PK-8); ENF-19(a) and ENF-S3 are read, not amended (1.7, inherited).

### (d) Absence of both local witnesses on a day with realized profit at or above the limit as its own lock reason

A TAMPER POSTURE rather than a reconstruction: if, at the SYNCING exit, `AgStateLoad` returned 1 (missing, not corrupt) AND `GlobalVariableCheck(AgGvLock())` is false (the GV absent, not merely zero-valued) AND today's reconstructed realized figure (from the existing `AgRealizedFold`/`AgRealizedRunFold` walk already running for other purposes) meets a threshold, treat the day itself as suspect and lock, independent of whether any specific breach can be reconstructed. **Threshold variants**, each named because they differ materially on LOCK TWO: (d-i) realized peak reconstructs to any value `> 0` (a day that ever made a profit at all, the loosest reading; both LOCK ONE and LOCK TWO qualify, and so would almost every ordinary trading day, making this the most aggressive variant); (d-ii) realized peak reconstructs to `>= limit_cmp` (a day whose peak alone would have breached, matching the ordinary peak breach condition; both locks qualify, since both breached ON the peak path by definition); (d-iii) CURRENT reconstructed realized `>= limit_cmp` (LOCK ONE qualifies at relaunch, realized 198.12 or 202.83 against 147.54; LOCK TWO does NOT qualify, realized 113.50 against 158.69, since the day's peak was given back before the drill and the current realized figure alone never reached the limit, this variant FAILS to close LOCK TWO's own opening TWO, the exact case this document's finding 2 names). **Reason variants:** lock with `AG_LOCK_CORRUPT_STATE` (reusing the existing reason and its journal text, `AgLockReasonName`, `State.mqh`, not quoted here in full), naming the record untrustworthy, which is arguably true; or a NEW reason value inside the same `L|` record field (already an int, `Persist.mqh:355`, so no format change, 1.7), naming the posture explicitly, e.g. "WITNESS_ABSENT", which needs its own journal string and its own `AgLockReasonName` case but touches no persisted format. **Cost, named plainly:** a legitimate FRESH INSTALL, a new data folder, or the R8 VPS move (`LEDGER.md:1921`, "the real account will run on an always-on VPS. Deployment to it is by git sync, never by manual edits in the terminal install folder") all produce EXACTLY the same signature, missing state file and missing GV, on a day that may have realized profit for entirely ordinary reasons; every one of these locks a legitimate fresh attach with no tamper at all. The GV's own 4-week TTL (`SPEC:72`, "The 4-week GV lifetime is irrelevant at 1 s refresh", true only while the EA keeps running; a genuinely idle account whose GV expires unattended would present the same signature) is a further ordinary route to the same state. **Defeated by:** the forged-file case named in 1.5, a present file with a forged-valid checksum claiming `lock_reason=NONE`, plus a GV explicitly set to 0 rather than left absent, both indistinguishable from an honest abstention (`DESIGN:87`); (d) tests for ABSENCE, not for CONTENT, so it closes nothing against that specific forgery, exactly as every other option in this section also does not (no option in this document defends against a locally-recomputed forged checksum, which is out of scope for a witness that reads what is present rather than authenticates it).

### (e) Reconstruct the floating path from deal history plus server tick history

Examined and not worked in the same depth as (a) through (d), because it reaches outside the fold this project's source has ever run: a floating give-back needs the price AT THE MOMENT OF GIVE BACK, which the guardian's own `POSITION_PROFIT` read (`Pnl.mqh:278`, `AgFloating()`) only ever samples live, once per tick, and never persists; MT5 exposes no per-tick price HISTORY API this codebase calls anywhere (grep of the tree for `CopyTicks`, `CopyRates` at `6c82281` returns zero hits). ### (f) A further local witness

Examined and closed on the record already made for the ratchet floor: `DESIGN:259` (the ratchet fold-in's own residual note, quoted in 1.7 by reference) states plainly that ANY further local artifact "narrows, [it does] not close" the same class of gap, and is defeated by the identical local-deletion-plus-input-inflation route every existing local witness already concedes to (`SPEC:144`). (b) and (c), when they fire, move the re-lock from the ACTIVE pass (finding 1, step 6-7) to the SYNCING exit (the intact path's own step, `EA:1254`), closing opening ONE for the cases each one covers; the delta this removes is the single tick quantified in 2.4. ### Named and closed: anything that would let the guardian send an order outside LOCKED

Not proposed anywhere in this section, and named explicitly because a "marker order" or "peak token" sent from ACTIVE or at boot, purely to plant a fresh server-side witness ahead of any real breach, was considered and is closed on three grounds together: it would be the first trade API call reachable from anywhere but `Sweep.mqh`'s own LOCKED-gated paths (ENF-S3, ENF-S2, 1.7, both INHERITED by every option actually proposed), it would contradict "EA cannot close terminal or disconnect from broker.
